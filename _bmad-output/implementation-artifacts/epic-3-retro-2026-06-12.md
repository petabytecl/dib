## What Went Well

1. Command routing stayed explicit and inspectable.
   Evidence: `Definition.Route(args)` returns route snapshots and typed errors, exposes canonical paths and raw match tokens, preserves remaining args, and avoids `os.Args`, stdout/stderr mutation, and `os.Exit`.

2. Epic 2 lessons were applied.
   Evidence: Story 3.3 consumes exported `flags.Set.Parse`, `flags.Set.Definitions`, `flags.Snapshot`, and typed `flags` diagnostics rather than duplicating parser syntax.

3. Public diagnostics remained machine-readable.
   Evidence: Unknown command, alias validation, duplicate command token, and flag-composition failures use sentinels or typed errors with `errors.Is` / `errors.As` contracts and accessor methods.

4. Rendering stayed caller-owned and deterministic.
   Evidence: `Definition.WriteHelp`, `Definition.WriteUsage`, `Result.WriteHelp`, and `Result.WriteUsage` write only to caller-supplied writers, return writer errors directly, omit hidden flags, and avoid sensitive values.

5. Execution boundaries were modeled without lifecycle ownership.
   Evidence: `command.Boundary`, `command.NewBoundary`, and `Definition.RouteBoundary` package route results with caller context, args, stdout, and stderr metadata without invoking callbacks, writing streams, deciding exit policy, or importing `config/`.

6. Verification discipline remained strong.
   Evidence: Story records show focused command tests, `go test ./...`, `go vet ./...`, `go run ./tools/depgate`, `git diff --check`, and race tests passing. QA automation added boundary-specific coverage in Story 3.5.

## Key Insights

1. The route snapshot is now the central command contract.
   Canonical path, raw match tokens, remaining args, composed flags, and parsed flag snapshots give callers enough state to assert behavior without process side effects.

2. Boundary metadata is the right Epic 3 endpoint.
   Story 3.5 satisfied FR2's execution-boundary requirements without inventing callback dispatch or lifecycle ownership. Actual invocation remains a future architecture/API decision.

3. Help and usage are product contracts, not incidental strings.
   Story 3.4 proved deterministic rendering with exact-output tests, structured assertions, redaction checks, and direct writer-error behavior.

4. Documentation evidence needs the same review discipline as code.
   Epic 3 implementation quality was high, but file-list drift and stale scope wording show documentation must be verified against code and tests at the end of each epic.

## Next Epic Preview

Epic 4 is "Provenance-Aware Config Resolution." It depends on Epic 3 and Epic 2 in these ways:

- Config flag binding should consume exported flag snapshots or a small exported source interface; it must not depend on `command/` internals.
- Config source labels must remain exactly `default`, `explicit setter`, `flag binding`, `env`, and `JSON`.
- Config diagnostics must preserve typed error inspection and redaction behavior established by `flags/` and `command/`.
- Config APIs must keep explicit readers, env lookup, setters, and JSON sources rather than reading ambient process state.
- Config resolution must stay independently usable, with callers composing it with command routing and flag parsing.

No significant Epic 3 discovery requires rewriting Epic 4's planned stories. The main readiness need is to carry the same evidence pattern into config: typed errors, provenance snapshots, redaction tests, behavior-matrix rows, dependency-gate verification, and artifact file-list checks.
